## 1. 项目背景与目标

面向国内跨境电商卖家，提供从商品实体图到电商信息与商品套图的一站式 AI 工具。

用户上传一张或多张真实商品图，补充商品规格、卖点、目标受众和生成要求，可选上传风格参考图与一份产品说明书。系统通过 AI：

- 分析商品信息并生成英文电商文案及中文解释。
- 规划符合目标平台的图片组合。
- 生成商品主图、功能卖点图、使用场景图和细节图。
- 检查生成图片与真实商品之间的一致性风险。
- 保存项目历史，支持单张重生成和批量下载。

产品的目标能力不是简单换背景或把原始照片重新美化，也不是针对灭蝇灯等单一商品编写专用规则。系统应覆盖若干预先支持的商品大类：从用户上传的一张商品实拍图或主图中识别或确认所属大类、具体商品主体、配件、包装、可见结构与不确定信息，加载该大类的卖点框架、常用场景、细节检查项、合规边界和视觉模板，基于图片证据和用户确认信息提炼市场卖点，再围绕同一商品主体生成具有电商信息图表达的主图、功能图、场景图和细节图。Temu 等平台商品图只作为构图、信息层级、场景氛围、局部放大与图标排版的视觉语言参考，不作为商品功能和参数的事实来源。

### 成功标准

- 用户不需要掌握提示词即可完成一次套图生成。
- 商品主体的颜色、形状、材质、Logo、数量和配件尽量保持一致。
- 四类图片围绕同一个已确认商品主体展开，不把包装、说明书或配件误识别为主商品，也不把参考图中其他商品的结构和功能迁移到当前商品。
- 功能图、场景图和细节图应各自表达明确购买理由，而不是重复生成四张相似的产品陈列照。
- 所有卖点、参数、用途和功效均可追溯到上传图片、说明书或用户确认；只有市场表达方式可以由 AI 策划，商品事实不得由 AI 猜测。
- 同一套核心流程通过可配置的类目画像服务多个商品大类，类目差异集中在事实字段、卖点候选、场景候选、细节检查、合规规则和模板选择，不在业务代码中为单品硬编码。
- 英文标题、关键词和卖点可直接编辑和复用。
- 主图符合目标平台的基础规则，营销图可用于进一步人工审核与发布。
- 任务失败不会重复收费，成功结果不会因部分失败丢失。

### 目标用户

- Amazon、Shopify、TikTok Shop 等平台的中国跨境卖家。
- 电商运营、设计和商品上架人员。
- 缺少稳定设计资源、需要快速制作多商品素材的小团队。

## 2. MVP 范围

### 2.1 首期包含

- 邮箱账号登录与用户数据隔离。
- 项目创建、项目列表和历史记录。
- 上传 1–10 张商品图。
- 可选上传 0–4 张风格参考图。
- 可选上传 0–1 份 PDF、DOC 或 DOCX 产品说明书。
- 商品图、风格参考图和产品说明书均支持点击选择或拖拽上传。
- 填写商品名称、品类、规格、材质、目标人群、真实卖点和额外要求。
- AI 生成英文标题、关键词、卖点和商品描述，并提供中文对照。
- 用户编辑并确认 AI 分析结果。
- 默认生成 4 张 1:1 电商套图。
- 查看生成进度、失败原因和一致性检查结果。
- 修改文案、修改生成要求、单张重生成。
- 下载单张 PNG/JPG 或整套 ZIP。
- 额度余额、预扣、消费、失败退款和流水记录。
- 私有测试环境部署和完整本地运行方式。

### 2.2 首期不包含

- 真实支付、套餐购买和发票。
- 自由拖拽、图层、抠图等完整画布编辑器。
- 批量 SKU 或 Excel 批量生图。
- 服装虚拟试穿和模特换装。
- 商品视频生成。
- 团队空间与多人协作。
- 自动发布到电商平台。
- 多 AI 供应商自动路由。
- 食品、医疗、保健、美妆功效等强监管品类的合规承诺。

## 3. 用户流程与功能设计

### 3.1 核心流程

1. 用户注册或登录。
2. 创建项目并选择目标平台，默认 Amazon US。
3. 点击选择或拖拽上传商品实拍图，可选上传风格参考图和一份产品说明书。
4. 填写商品事实、卖点、规格和生成要求。
5. AI 分析并返回结构化双语商品信息。
6. 用户检查和修改分析结果。
7. 系统创建 4 个独立生成任务，最多并发执行 2 个。
8. 每张图片生成后执行商品一致性检查。
9. 用户查看结果，可修改文案、确认风险或单张重生成。
10. 下载单图或套图 ZIP，项目保存在历史记录中。

M6 目标流程在步骤 5–7 之间增加类目与商品视觉身份确认：系统先识别或让用户选择受支持的大类，再区分主商品、配件、包装和背景，按类目画像列出可见结构、证据化卖点、推测项与缺失信息；用户确认或修正后，系统按不同图种生成结构化构图方案，再创建图片任务。风格参考图只提取版式和视觉语言，不参与商品事实识别。

### 3.2 默认四图

| 图种        | 主要目标             | 默认规则                                       |
| ----------- | -------------------- | ---------------------------------------------- |
| 白底主图    | 展示真实商品主体     | 纯白背景、无营销文字、无无关道具、商品完整展示 |
| 功能卖点图  | 表达一个核心购买理由 | 商品主体加简短英文卖点，文字由确定性模板排版   |
| 使用场景图  | 展示真实使用情境     | 场景不得虚构商品不具备的用途、尺寸或效果       |
| 材质/细节图 | 展示做工、接口或材质 | 只突出真实存在且在原图或用户信息中可验证的细节 |

默认输出 2048×2048，提供 PNG 和 JPG。若模型原始输出尺寸不同，由导出层统一规范化。

### 3.3 文案和图片分层

- AI 优先生成无文字商品视觉。
- 营销文字通过固定模板叠加，避免模型生成错误英文。
- MVP 不提供自由画布编辑器。
- 用户修改文字后免费重新合成图片。
- 用户要求改变场景、构图或商品展示方式时，触发付费的视觉重生成。

### 3.4 一致性检查

生成图与原商品图对比检查：

- 商品颜色、形状和主要结构。
- Logo、图案和品牌标识。
- 材质和表面纹理。
- 商品数量、套装内容和配件。
- 尺寸比例与使用场景。
- 是否出现用户没有声明的功能、性能或认证。

检查结果分为：

- `passed`：未发现明显差异，可正常下载。
- `review_required`：存在潜在差异，提示用户重生成或确认后下载。
- `blocked`：内容安全拒绝、文件损坏或生成失败，不产出可下载结果。

自动检查只是辅助，最终商品真实性仍需商家人工确认。

### 3.5 商品主体理解与电商视觉策划（M6 目标）

- 建立可版本化的 `CategoryProfile`：定义大类识别标签、必要事实字段、可用卖点类型、典型场景、关键细节、禁用声明、平台约束和适配的信息图模板。
- 模型可建议商品大类，但在低置信度、跨类或不受支持时必须让用户选择或确认；具体商品仍由通用视觉身份结构描述，不为灭蝇灯等单品硬编码规则。
- 从实拍图或主图中确定唯一主商品，并区分配件、包装、说明书、背景道具和不确定物体。
- 建立可复用的商品视觉身份：整体轮廓、颜色、材质、Logo、关键结构、接口、按钮、数量关系、可拆装状态与禁止改动项。
- 每条卖点必须携带证据来源和置信度；尺寸、性能、认证、覆盖范围、噪声、续航、功效和适用环境等不可仅凭视觉推断。
- 参考商品图只抽取布局类型、主体位置、信息密度、背景氛围、局部放大方式、图标与文案区域；禁止复制参考商品的显示屏、接口、灯效、配件、参数或功能。
- 图片模型优先生成无文字的主体和场景底图；标题、图标、箭头、尺寸线、参数卡片和局部放大框由确定性模板合成。
- 四图需要明显差异化：主图负责商品识别，功能图解释一个已确认卖点，场景图展示已确认用途，细节图展示真实结构或配件。

## 5. 技术选型

### 5.1 已确认技术栈

| 层级        | 选择                                                    | 说明                                 |
| ----------- | ------------------------------------------------------- | ------------------------------------ |
| 前端        | Next.js + React + TypeScript                            | 产品界面、SSR/CSR、上传和结果展示    |
| API 服务    | NestJS + TypeScript                                     | 鉴权、项目、额度、任务和文件接口     |
| 异步 Worker | NestJS Standalone + BullMQ                              | AI 分析、生图、检查、合成和失败重试  |
| 主数据库    | PostgreSQL                                              | 用户、项目、任务、额度和事务数据     |
| ORM/迁移    | Drizzle ORM                                             | 类型安全且保留清晰 SQL 控制          |
| 队列与缓存  | Redis + BullMQ                                          | 任务队列、限流、锁、进度和短期缓存   |
| 文件存储    | 本地 MinIO；生产 S3/R2/OSS                              | 保存原图、参考图和生成结果           |
| 反向代理    | Nginx                                                   | HTTPS、域名、上传限制和服务转发      |
| 部署        | Docker Compose                                          | 本地和服务器环境尽量一致             |
| AI 供应商   | OpenAI，服务端密钥                                      | 首期单供应商，通过适配层隔离业务代码 |
| Monorepo    | pnpm workspace                                          | 管理三个应用与共享包，锁文件保证复现 |
| 基础工具链  | Node.js 22、TypeScript 5.9、ESLint 10、Prettier、Vitest | 统一构建、检查、格式与测试基线       |

### 5.2 为什么首期使用 Node.js/TypeScript

- 前后端共享类型、枚举和校验 Schema，减少接口偏差。
- 主要负载是文件和网络 I/O、AI API 等待与任务编排，适合 Node.js。
- NestJS 对模块、鉴权、依赖注入、测试和 BullMQ 有成熟支持。
- API 与 Worker 可使用同一套领域服务，又能独立部署和扩容。

### 5.3 Python 的使用边界

首期不引入 Python。出现以下需求时，再增加独立 Python AI Worker：

- 本地部署生成模型或 GPU 推理。
- SAM 抠图、YOLO 检测、复杂 OCR。
- OpenCV/Pillow 大批量处理。
- 模型训练、微调或自研一致性算法。

Python 服务不得直接替代核心账务和项目数据的事务控制；通过队列接受任务并返回结构化结果。

### 5.4 为什么使用 PostgreSQL

- 额度预扣、流水、退款和任务创建需要可靠事务。
- 用户、项目、素材和任务具有清晰关系，适合外键和约束。
- `jsonb` 可保存模型结果、Prompt 元数据和检查结果，并支持索引。
- 后续可使用全文搜索和 `pgvector`，无需过早引入额外搜索数据库。

Redis 不是业务主数据库。用户余额、任务最终状态和额度流水以 PostgreSQL 为准；Redis 只保存可恢复的队列和临时状态。

图片文件不得以 Base64/BLOB 形式长期存入 PostgreSQL，只保存对象存储 Key、格式、尺寸、哈希和状态。

## 6. 系统架构

```text
Browser
  │
  ▼
Nginx
  ├── Next.js Web
  └── NestJS API
         ├── PostgreSQL
         ├── Redis / BullMQ
         ├── S3-compatible Object Storage
         └── OpenAI-compatible API（短请求或任务提交）

Redis / BullMQ
  │
  ▼
NestJS Worker
  ├── OpenAI-compatible 图片生成
  ├── OpenAI-compatible 一致性检查
  ├── 文字模板合成
  ├── Object Storage
  └── PostgreSQL 状态与流水更新
```

M3 的每张图片都是独立 BullMQ 任务，Worker 全局并发固定为 2。任务从 PostgreSQL 读取不可变输入快照和素材 ID，依次执行素材预处理、OpenAI 图片编辑生成、2048×2048 PNG 规范化、一致性检查、对象存储写入和事务结算。PostgreSQL 保存最终任务状态、0–100 进度、阶段和额度流水；Redis 只负责投递和重试。

M4 导出由 API 同步执行：读取各角色最新成功生成图和项目当前已保存的 `imagePlan.copyEn`，通过 `image-layout` 中的固定 SVG 模板与 Sharp 合成 2048×2048 图片。主图始终跳过文字层；feature、lifestyle、detail 分别使用固定的底部渐变、顶部卡片和底部细节卡片。单图保存为 PNG 或 92 质量 JPG，整套按 main、feature、lifestyle、detail 顺序打包为不重复压缩的 ZIP。导出资产保存在私有对象存储并写入现有 `assets` 表，按内容 SHA-256、文件名和项目复用，不产生额度流水。

M5 初始化新增一条生产安全与可观测性基线：API 为所有响应分配或透传 `x-request-id`，记录不含查询参数、Cookie、请求体、Prompt 和图片的 JSON 访问日志；登录注册、上传、分析、生图及重试以 Redis 原子计数按来源 IP 限流，Redis 不可用时这些敏感写接口以 503 失败关闭。生产 Compose 仅暴露 Nginx，Web、API、Worker 与外部托管 PostgreSQL、Redis、S3 服务通过内部网络连接；Nginx 负责 TLS、安全头、基础每 IP 限流和请求 ID 透传。由于 M2 分析仍同步等待模型结果，本地与生产 API 代理读取/发送超时均为 180 秒，避免中转站正常慢响应被默认 60 秒代理超时截断。

对象存储使用内外双端点：`S3_ENDPOINT` 供 API/Worker 在容器网络内读写，`S3_PUBLIC_ENDPOINT` 只用于生成浏览器可访问的签名读取地址。本地 Compose 默认分别为 `http://minio:9000` 和 `http://localhost:9000`；生产环境的公开端点必须配置为用户可访问且与签名 Host 一致的对象存储或 CDN 域名。

素材上传继续由 API 代理完成。商品图与风格图支持 JPG/PNG/WebP，产品说明书支持 PDF/DOC/DOCX；三类上传都校验客户端 MIME 与二进制签名，说明书还要求扩展名匹配。单文件统一限制 15 MB，说明书每项目最多一份并保存到同一私有对象存储。当前说明书仅作为可查看的项目附件，不进入 OpenAI 输入；未来接入文本抽取前需补齐解析沙箱、提示注入隔离和内容安全策略。

### 部署进程

- `web`：前端服务。
- `api`：HTTP API，不执行耗时生成任务。
- `worker`：独立任务消费者，可按生图并发量横向扩容。
- `postgres`：生产优先使用托管数据库；本地由 Docker 提供。
- `redis`：生产开启持久化和备份；本地由 Docker 提供。
- `minio`：仅本地或私有部署使用；生产可切换为 S3/R2/OSS。

当前本地 Compose 使用固定版本 `bitnamilegacy/minio:2025.7.23-debian-12-r5`。这是由于 2026-10 验收时上游官方预构建镜像无法匿名拉取的临时兼容方案，只限本地开发；生产不得直接沿用该 Legacy 镜像。

## 7. AI 处理流程

### 7.1 模型分工

当前默认模型配置：

- 商品识别与结构化文案：`gpt-6.1-sol`。
- 商品图片生成与编辑：`gpt-image-2.5-sunburst`。
- 生成后一致性检查：`gpt-6-luna`。

模型 ID 必须通过环境变量或配置表管理，不能散落在业务代码中。上线前重新核对可用性、价格和组织权限。

AI 访问支持 OpenAI-compatible 中转站：设置含 `/v1` 的 `OPENAI_BASE_URL` 和 `OPENAI_ANALYSIS_API_KEY`、`OPENAI_IMAGE_API_KEY`、`OPENAI_REVIEW_API_KEY` 后，分析、生图和一致性检查分别使用独立 Key 与独立 SDK 客户端。三把专项 Key 只要设置任意一把，即启用专项模式，绝不再混用旧的 `OPENAI_API_KEY`。后者保留为官网直连兼容回退，仅在三把专项 Key 均为空时使用。生产启动会拒绝缺失任一专项 Key 的部分配置，并要求已设置的 `OPENAI_BASE_URL` 使用 HTTPS。

### 7.2 Provider 接口

```ts
interface AiProvider {
  analyzeProduct(input: ProductAnalysisInput): Promise<ProductAnalysisResult>;
  generateImage(input: ImageGenerationInput): Promise<GeneratedImageResult>;
  reviewConsistency(
    input: ConsistencyReviewInput,
  ): Promise<ConsistencyReviewResult>;
}
```

首期只有 `OpenAiProvider`。业务服务依赖接口而不是直接依赖 OpenAI SDK，以便后续增加其他供应商或自建模型。

M2 使用 Responses API 的图片输入与严格 Structured Outputs。模型输出先由 OpenAI SDK 按 JSON Schema 解析，再由共享 Zod Schema 二次校验业务约束；拒绝、不完整响应和 Schema 失败统一作为分析失败并触发退款。商品原图从私有对象存储读取后，仅在内存中生成最长边 2048 像素、85% 质量的 JPEG 分析副本，避免 Base64 输入超过单图长度边界，原始对象不变。

M3 使用 Images Edit API，将最多 10 张商品原图作为权威商品参考、最多 4 张风格图作为仅限风格的参考输入，输出 1024×1024 PNG 后由 Worker 规范化为 2048×2048。四种角色使用版本化确定性 Prompt：所有 AI 视觉都禁止模型生成文字，主图额外强制白底、无道具和完整商品；营销文字留给 M4 模板合成。一致性检查使用 Responses API 严格结构化输出，对比颜色、形状、结构、Logo、材质、数量、配件、比例与未验证声明，结果为 `passed` 或 `review_required`。

M6 将替换“把整张上传图直接视为商品主体”的现有假设。分析阶段需要先产出 `productVisualIdentity` 和证据化 `marketableFacts`，生图任务只把已确认的主商品身份、允许出现的配件及角色化构图方案作为约束。必要时生成或保存标准化商品主体参考资产，但该资产必须继续与原始实拍图做一致性校验，不能反向成为未经验证事实。参考图分析结果应保存为抽象视觉模板，不直接向生图模型传递其中商品的具体结构和功能。

M6 的类目能力采用配置与 Schema 驱动：先由 `CategoryProfile` 约束该大类应询问和验证的事实、允许策划的卖点类型、典型但需确认的使用场景、合规风险和可选模板，再由通用商品视觉身份描述具体 SKU。新增大类应主要通过增加版本化类目配置、示例与测试完成，而不是复制生图流程或增加单品条件分支。

所有创建任务或扣费接口必须支持 `Idempotency-Key`。API 使用统一错误结构：

M2 的分析接口当前采用同步 HTTP 调用：事务内预扣 1 额度并写入 `running` 任务，Provider 成功后原子保存分析结果与 `consume` 流水；任何已捕获失败会原子标记任务失败并写入 `refund` 流水。相同 `Idempotency-Key` 不重复调用或扣费。分析结果编辑保存不扣额度。

M3 的 `POST /api/projects/:id/generations` 空请求体创建完整四图，传入 `{ "role": "main|feature|lifestyle|detail" }` 创建单图重生成。完整请求在一个 PostgreSQL 事务中创建 4 个独立任务并分别预留 3 额度；单图任务预留 3 额度。API 提交 BullMQ 失败时立即标记任务失败并退款。`GET /api/projects/:id/jobs` 和 `GET /api/jobs/:id` 返回任务阶段与进度；`POST /api/jobs/:id/retry` 只允许重试失败图片任务，并以新的幂等键和独立 3 额度创建新任务。临时错误最多指数退避重试 3 次，业务输入错误、安全拒绝、无密钥和无效响应直接进入最终失败退款。

## 10. 额度规则

MVP 默认规则：

| 操作                     |                 额度 |
| ------------------------ | -------------------: |
| 首次注册赠送             |                  +50 |
| AI 商品分析              |                   -1 |
| 完整四图                 |                  -12 |
| 单张视觉重生成           |                   -3 |
| 修改文字并重新合成       |                    0 |
| 模型失败、超时或安全拒绝 | 自动退回对应预留额度 |

处理原则：

1. 在 PostgreSQL 事务中检查余额、创建任务、预留额度并写流水。
2. Worker 成功后把预留转换为实际消费。
3. 失败只退回失败任务对应额度，已成功图片保留。
4. 相同幂等键不得创建第二个任务或重复扣费。

## 11. 安全、隐私与非功能要求

### 安全

- 密码使用 Argon2id 或等效安全算法哈希。
- 登录使用安全、HttpOnly、SameSite Cookie；生产环境强制 HTTPS。
- OpenAI 和对象存储密钥只存在于服务端 Secret/环境变量。
- 上传时校验 MIME、扩展名、文件头和大小；图片额外校验像素尺寸。
- 对象存储默认私有，访问需要鉴权或短期签名 URL。
- 所有项目、文件、任务和下载接口执行服务端归属校验。
- 日志不记录用户原图内容、完整 Prompt、密码和密钥。
- 对登录、上传、分析和生成接口实施限流。

M5 初始化已实现 API 级 Redis 限流（默认：登录/注册 10 次/15 分钟、上传 30 次/小时、分析 10 次/小时、生图与重试 30 次/小时）和 Nginx 10 请求/秒的基础保护；限额可通过环境变量调整。API 设置 `nosniff`、拒绝嵌入、严格 Referrer Policy、最小 Permissions Policy、无缓存 API 响应及请求 ID。生产 Nginx 额外设置 HSTS、CSP 和 TLS 1.2/1.3。

### 可靠性

- API 重启不丢失已提交任务。
- Worker 使用指数退避重试；业务错误和安全拒绝不盲目重试。
- 任务状态、额度状态与对象文件写入需设计补偿流程。
- 生成任务支持超时和僵尸任务回收。
- PostgreSQL 定期备份；对象存储启用版本控制或生命周期策略。

### 性能基线

- 普通 API P95 目标小于 500ms，不包含上传和 AI 调用。
- 项目列表分页读取。
- 四图默认最多并发 2 张，避免单用户瞬时占满模型额度。
- 上传和下载不通过数据库中转大文件。

## 14. 总体验收场景

- 上传 1 张、10 张商品图和 0–4 张风格图。

- 刷新、退出和重新登录后可恢复项目状态。
- 用户无法访问其他用户的项目、任务、图片或下载地址。

- M6 首批支持的商品大类、每类代表性验收 SKU，以及不支持或需要额外合规审核的类目边界。

### 已知风险

- 生成模型无法绝对保证商品一致性，必须保留人工确认步骤。
- 平台图片规则会变化，需要把规则做成可版本化配置。
- 生图成本与延迟受模型、尺寸、质量和参考图数量影响，需要记录真实用量后调整额度。
- Redis 任务与 PostgreSQL 业务事务之间存在双写风险；M3 已实现幂等任务、API 入队失败退款和 Worker 幂等结算，但 Redis 数据丢失后重新投递数据库 `queued` 任务的补偿扫描尚未实现。
- 图片上传和生成可能造成存储成本增长，需要生命周期和删除策略。
- MinIO 上游已转向源码分发且官方预构建镜像当前不可稳定拉取；本地临时使用的 Bitnami Legacy 镜像不再维护，需持续做漏洞扫描，并在生产部署前确定受维护的 S3 兼容服务或自建镜像方案。
- Docker 构建默认 npm 镜像源是可配置的第三方镜像；CI/生产应按组织供应链政策设置 `NPM_REGISTRY`，并始终使用冻结锁文件和完整性校验。
- M1 的 API 代理上传适合当前 15 MB 上限；文件变大或并发升高时需引入预签名直传并保留 complete 校验步骤。
- 项目当前采用软删除，对象文件尚未由后台任务批量回收；进入生产前需实现清理队列和失败补偿，避免孤儿对象累积。
- 数据库会话当前为固定 30 天有效期；生产上线前需增加过期会话定期清理，并结合账号安全策略评估滚动续期和全设备退出。
- M2 的分析模型成功路径尚未使用真实 OpenAI 测试密钥联调；当前已覆盖请求构造、Schema 和失败补偿，上线前必须确认模型权限、实际输出质量、延迟和费用。
- M3 的图片生成和一致性检查成功路径尚未使用真实 OpenAI 测试密钥联调；当前已覆盖请求构造、严格 Schema、队列执行和最终失败补偿，上线前必须逐角色确认模型权限、参考图一致性、实际输出质量、延迟和费用。
- M2 分析调用仍在 API 请求内同步执行；进程在预扣后被强制终止可能留下 `running` 任务和未释放额度。M3 只将图片链路迁入 BullMQ，分析异步化、超时任务扫描与僵尸任务幂等补偿仍须在生产准备前完成。
- 同步分析的中转站完整响应已观测到约 106 秒；当前 Nginx 统一给出 180 秒窗口，但网络或供应商尾延迟仍可能超窗，并在后端最终完成后向浏览器表现为失败。分析异步化与可查询的后台任务状态仍是根治方案。
- M3 对临时错误自动重试最多 3 次，但当前没有用户取消正在运行图片任务的 Worker 中断机制；公开取消接口前需确定 OpenAI 请求取消、已发生费用和额度结算规则。
- M4 导出当前在 API 进程中同步读取并合成最多四张 2048×2048 图片，适合 MVP 固定套图；扩展到批量 SKU 或更多高分辨率图片前需改为异步任务或流式 ZIP，避免 API 内存与请求时长增长。
- export 资产与其他对象目前共用尚未完成的生命周期清理机制；频繁修改文案会产生不同内容的历史导出，进入生产前需纳入项目删除和定期清理策略。
- M5 的生产编排和运维工具已完成仓库内验证，但尚未使用真实云数据库、Redis、对象存储、域名和 TLS 完成部署；外部资源选型、网络访问控制、证书续期、监控接收端和对象存储版本/生命周期策略仍需按最终供应商落地。
- API 限流按来源 IP 计数，适合作为第一层保护；未来多地域、多代理或企业网络场景应结合真实用户身份、WAF 规则和供应商限额调整阈值，避免共享出口误伤。
- 产品说明书当前只做二进制签名/MIME/扩展名校验和私有存储，尚未接入恶意文件扫描；共享或公开下载前应增加防病毒与内容安全扫描。旧版 DOC 的 CFB 容器签名只能证明文件容器类型，不能替代恶意内容扫描。
- 产品说明书当前不参与 AI 分析；未来若解析 PDF/Word 文本，必须把文档内容视为不可信数据，并补齐解析资源上限、提示注入隔离、隐私提示和输入长度控制。
- OpenAI-compatible 中转站必须实际兼容 Responses API（含结构化输出与图片输入）和 Images Edit API；配置格式兼容不代表模型、参数、限额或错误码完全兼容，必须以三条受控真实调用分别验收。
- 单张实拍图可能存在遮挡、低分辨率、包装图与实物冲突或无法判断配件归属；M6 必须显示不确定项并允许用户确认，不能用市场常见配置自动补全商品事实。
- 竞品营销图可能包含夸大、错误或属于其他 SKU 的参数和结构；只允许抽取抽象版式与视觉语言，并对生成文案、图标和视觉特效继续执行证据校验。
- 主体标准化资产本身也可能产生结构漂移；若引入主体提取或标准白底参考图，必须保留原图为最高优先级事实源，并在后续每张生成图中同时执行原图一致性检查。
- 类目自动识别可能在跨类商品、组合套装和新型商品上失准；低置信度时必须回退到用户选择，并保证类目画像版本随生成任务快照保存以便复现。
